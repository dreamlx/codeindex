# Does `README_AI.md` actually help an agent? — 2026-05 benchmark

**Question being asked**: When a coding agent (claude-sonnet-4-6) investigates an
unfamiliar codebase, does giving it codeindex-generated `README_AI.md` files
measurably improve its answers — or does it just feel faster?

**TL;DR**: Across 15 hand-graded question pairs spanning 3 heterogeneous
projects, agents with `README_AI.md` access were on average **19% faster and
used 28% fewer tokens** — *but speed/cost gains masked a real quality problem*:
on 3 of 15 questions the WITH-README agent answered WRONG or PARTIAL where the
WITHOUT-README agent answered CORRECT. The fix shipped in
[ADR-005](../architecture/adr/005-navigation-disclaimer-and-readme-size-cap.md):
tighter README size cap (50KB → 10KB default) + a navigation-contract
disclaimer in every README header.

---

## Methodology

### Test projects (anonymized; profile matters more than name)

| Project | Type | Size | Familiarity to question-author |
|---|---|---|---|
| **A** | Python CLI / MCP server | ~10 scanned dirs, max README 2.6KB | own project |
| **B** | Python data-pipeline framework | ~50 scanned dirs, max README 6KB | own project |
| **C** | Legacy PHP admin/payment system | ~250 scanned dirs, multiple files >5000 lines, max README hit 50KB cap | third-party download, author unfamiliar |

Project C deliberately included the kind of tech-debt monster files codeindex
is most likely to be deployed against (the biggest single file was 8891 lines).

### Question generation

5 questions per project (15 total). To avoid bias-by-construction, each
project's questions were generated by a separate sub-agent forbidden from
reading `README_AI.md` while drafting — it could only inspect actual source
files, READMEs, configs. Each question came with a reference answer derived
from source.

Questions intentionally mixed:

- structural ("where is X implemented")
- behavioral ("trace the data flow for Y")
- architectural ("what's the relationship between A and B")

### Agent runner

`claude -p` with `claude-sonnet-4-6`, tools restricted to `Read,Glob,Grep`,
output-format JSON for metrics extraction, $0.50 budget cap per question.

Two variants per question:

- **WO** (without README): `--disallowedTools 'Read(**/README_AI.md)'` blocks
  the agent from opening any `README_AI.md` file. Agent must explore via
  Grep/Read directly.
- **WITH** README: full access (project files were already scanned with
  `codeindex scan-all --ai` using haiku for enrichment).

For each (project, question, variant) triple, the harness recorded:
wall time, API time, total tokens, cost, response text, any permission denials.

### Grading

A separate haiku call graded each response against its reference answer:
`CORRECT` (captures all major facts), `PARTIAL` (some facts missed/wrong),
`WRONG` (mostly wrong or hallucinated). Numerically: 1.0 / 0.5 / 0.0.

This LLM-as-judge layer is critical: **without it, the "WITH is faster + cheaper"
headline would have been the takeaway, when in reality those gains were partly
the agent producing worse answers with less work**.

### Phase F3 — supplemental size-cap experiment

The 51KB README on Project C's largest module was independently re-tested with
the README explicitly shrunk to 10KB (caps applied per-directory). Same 3
questions targeting that module were re-run to isolate the size-cap effect.

### Phase J — disclaimer + tool-selection-guide A/B

The 3 questions where `WITH=WRONG/PARTIAL but WO=CORRECT` in the main run
were re-tested in 3-way: (a) WO baseline, (b) WITH-disclaimer-only, (c)
WITH-disclaimer + a tool-selection guide injected via
`--append-system-prompt`. This isolated whether the disclaimer alone was
sufficient or whether agents needed a more prescriptive instruction set.

## Headline results

### Project-level averages (15-question main run)

| Project | WO time | WITH time | Δtime | WO tokens | WITH tokens | Δtokens | WO grade | WITH grade | Δgrade |
|---|---|---|---|---|---|---|---|---|---|
| A (small Python) | 320s | 197s | **-39%** | 924K | 613K | -34% | **0.90** | **0.60** | **-0.30** ❗ |
| B (medium Python) | 272s | 185s | -32% | 1040K | 588K | -43% | 0.60 | 0.70 | +0.10 |
| C (large legacy PHP) | 430s | 445s | +3% | 1040K | 960K | -8% | 0.50 | 0.60 | +0.10 |
| **TOTAL / avg** | **1023s** | **826s** | **-19%** | **3.0M** | **2.2M** | **-28%** | **0.67** | **0.63** | **-0.04** |

Reading: across the whole sample, the speed/token gains the headline numbers
showed are real, but **quality is a wash on average and tilted negative on the
small-Python project where you'd most expect README to help** (own code, fast
to verify).

### Per-question pattern (15 graded pairs)

Sorted by where README helped or hurt most:

| Bucket | Count | Examples |
|---|---|---|
| **README WIN** (faster + more correct) | 3 | trace-flow questions on Projects A and B |
| **README HELP** (faster, same grade) | 5 | mostly mid-complexity navigation Qs |
| **No effect (tie)** | 4 | trivial-to-find code on small files |
| **README HURT quality** | 3 | precise-mechanism Qs where README gave summary, agent stopped there |

The 3 HURT cases all matched the same failure pattern:

1. Question asks for a specific mechanism (a 3-step protocol, a precise dedup
   key set, a sys.path manipulation, etc.)
2. README mentions the topic in 1-2 lines of summary
3. Agent reads the summary, treats it as authoritative, paraphrases it
4. The paraphrase omits or misstates the actual detail
5. Agent answers faster than WITHOUT-README — and answers wrong

### Worst single example: Project C, "compare two 4000-line monster classes"

Same question, two README sizes:

| Setup | Time | Tokens | Grade |
|---|---|---|---|
| WO (no README) | 166s | 60K | PARTIAL |
| WITH 51KB README (uncapped) | 197s | **418K** (+588%) | PARTIAL |
| WITH 10KB README (capped via Phase F3) | 175s | 148K (-65% vs 51KB) | PARTIAL |

When the README was uncapped, the agent treated its 119-file symbol catalog as
a "must-read" and followed every breadcrumb across mentioned classes. Quality
was no better than just grepping source. Capping the README to 10KB cut token
cost dramatically without changing quality — *but the agent still couldn't
beat raw exploration on this open-ended comparison question*.

Conclusion specific to this question type: README is the wrong shape of
information for cross-module open-ended comparison. The structural index can
point you to the files, but cannot synthesize the actual semantic difference
between them.

### Phase J: did the disclaimer alone fix the quality regressions?

Tested on the 3 worst-failing questions from the main run, comparing WO vs
WITH-disclaimer vs WITH-disclaimer-plus-tool-selection-guide:

| Variant | Avg grade | Avg time | Avg tokens |
|---|---|---|---|
| WO (baseline) | 0.83 | 36s | 138K |
| WITH disclaimer | **0.83** (tied) | 30s | 85K |
| WITH disclaimer + guide | 0.67 (regression) | 32s | 109K |

Key result: **the disclaimer alone was sufficient** to recover quality on the
worst F1-failure case while still keeping the speed/token gains. The
additional tool-selection guide *hurt* — the explicit "drill into source"
instruction over-constrained the agent in one case, leading to redundant
investigation and a CORRECT → PARTIAL regression. Hypothesis: a tool-selection
table is instructive for confused humans; for sonnet-tier agents it reads as
over-constraint.

## What shipped as a result

### Two changes landed in codeindex

1. **`max_readme_size` default 50KB → 10KB** (commit `1e1a754`). The 50KB cap
   let a navigation README grow to roughly the same token cost as reading
   source directly, defeating its purpose.
2. **Navigation-contract disclaimer at top of every README** (commit `f270787`):
   ```
   <!-- codeindex navigation index — agent: drill into source via Read/Grep
        for precise mechanism; do not treat this as final word. -->
   ```
   An HTML comment so renderers ignore it; agents reading raw markdown see
   the contract explicitly. Defined once in `writers/__init__.py`, used by
   all 5 generation sites.

### Explicit non-decision: no CLAUDE.md tool-selection guide

A third candidate change (inject a per-task tool-selection table into the
project's `CLAUDE.md` or via `--append-system-prompt`) was tested in Phase J
and **rejected** because it hurt quality on average. The disclaimer alone
proved sufficient.

## Caveats

- **N = 15 questions, 1 grader pass.** Single-shot variance per question is
  high; treat any individual cell of the per-question table as anecdote.
  Aggregates across the 15 are meaningful but not statistically tight.
- **Reference answers were human-curated but not double-blind.** The grader
  (haiku) is itself an LLM with its own bias surface.
- **Agent fixed to claude-sonnet-4-6.** Other agents (gpt-5, gemini-2.x,
  haiku-as-investigator) may show different patterns. README usefulness is
  partly a function of the consuming agent's behavior policy.
- **Quality grading is 3-tier (CORRECT/PARTIAL/WRONG)**, intentionally coarse.
  Some "PARTIAL → PARTIAL" cells may actually contain interesting drift the
  scale can't see.

## Reproducing this

Everything needed is in [`bench/`](../../bench/) — `make setup` + edit yamls +
`make run` + `make grade` + `make report`. The 5-step workflow runs against
your own choice of projects/questions. Budget roughly $3–7 per full benchmark
on sonnet + haiku grader.

The full per-row data from this study lives outside the repo (contains actual
project file paths and code excerpts) but the aggregates and patterns above
are reproducible against any 3 similarly-shaped projects.
